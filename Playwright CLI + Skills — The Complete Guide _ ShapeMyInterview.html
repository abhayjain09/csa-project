01Why we need this

If you've been following along, you already set up Playwright MCP with the three agents — Planner, Generator, and Healer. It works. It's powerful. But there's a hidden cost that becomes obvious the moment you run agents at scale.

Every browser snapshot in MCP burns 15,000 to 25,000 tokens. Multiply that by a 20-step automation session, and you're at ~114,000 tokens per single task. Do it in CI nightly — costs pile up fast. And past ~60% context fill, LLM reasoning quality drops noticeably ("lost in the middle" problem).

Microsoft's own team saw this. In early 2026, they released @playwright/cli — a lighter, shell-based alternative. The official README puts it plainly:

From Microsoft's docs

"Modern coding agents increasingly favor CLI-based workflows exposed as SKILLs over MCP because CLI invocations are more token-efficient. They avoid loading large tool schemas and verbose accessibility trees into the model context."

This guide covers everything you need to switch to (or supplement with) the CLI approach:

  • Install Claude Code (and why it beats Copilot for CLI work)
  • Install Playwright CLI + Skills the correct way
  • Understand the SKILL.md file — the core primitive
  • Run Planner, Generator, and Healer via CLI (with SauceDemo)
  • See the token difference with real numbers
  • Learn when CLI wins and when MCP still wins

02What is CLI + Skills

Two words. Understand both.

CLI

@playwright/cli is a standalone shell tool from Microsoft. Same team as Playwright MCP, same Playwright engine underneath. Different interface — shell commands instead of MCP protocol calls.

Sample commands the CLI exposes:

bash Sample CLI commands 
playwright-cli open https://www.saucedemo.com --headed
playwright-cli snapshot
playwright-cli type e12 "standard_user"
playwright-cli type e13 "secret_sauce"
playwright-cli click e14
playwright-cli screenshot login-success.png
playwright-cli codegen

Each command is short. Each output is short. Agent runs commands like a human developer does — sequentially in a terminal.

Skills

Skills are Markdown guide files. They teach the AI agent how to use a specific tool correctly. Think of them as "onboarding docs for the AI."

Without Skills, an LLM would guess at CLI commands based on its training data — and often hallucinate. With Skills, the agent reads a clear reference and uses commands correctly.

Playwright CLI ships with 6-7 pre-built Skills covering:

  • Running Playwright tests — run, debug, manage test suites
  • Request mocking — intercept and mock network requests
  • Running Playwright code — execute arbitrary scripts
  • Browser session management — manage multiple browser sessions
  • Storage state — persist cookies and localStorage
  • Test generation — plan / generate / heal workflow (same three roles as MCP agents, but via CLI!)
The important realization

The Planner-Generator-Healer workflow you already know from the MCP session works via CLI too. The three roles are preserved. What changes is the plumbing underneath — how the agent interacts with the browser.

Together

Skills tell the agent what commands exist and when to use them. CLI provides the actual commands. Combine them, and the agent has a lean, terminal-based way to drive browsers — without loading heavy tool schemas or streaming snapshots into context.

MCP is the protocol path. CLI + Skills is the shell path. Same job, different economics.

03Claude Code vs Copilot — why we're switching

For MCP, we used Copilot Chat in VS Code. That worked. For CLI + Skills, we're switching to Claude Code. This isn't fashion — it's fit for purpose. Here's the honest breakdown.

The core difference

Copilot Chat
IDE-centric. Chat panel inside VS Code. Great for inline code suggestions, decent for MCP tools. Terminal integration is possible but feels bolted on.
Claude Code
Terminal-native. Runs directly in your shell. Discovers Skills automatically from .claude/skills/. CLI-first workflows are its native mode, not an add-on.

Six reasons Claude Code wins for CLI work

1. Native terminal environment

Claude Code runs in your terminal. When it uses playwright-cli open ..., it's literally running that shell command as you would. No abstraction, no wrappers. Same environment, same errors, same behavior — every time.

Copilot Chat runs in a VS Code side panel. Terminal commands work, but they go through an approval flow, a different execution context. Debugging is harder because you're one abstraction removed from what's happening.

2. Auto-discovers Skills

Claude Code scans .claude/skills/ in your project (and in ~/.claude/skills/ globally) on startup. Any Skill you install becomes available immediately.

Copilot's Skills format is different and still evolving. Playwright CLI's Skills folder structure is designed for Claude Code first — that's where it lands out of the box.

3. Bigger context window (1M tokens on Opus)

Claude Code with Opus 4.8 gives you a 1 million token context window. Even if you occasionally read large snapshots or long files, you have room. Copilot's context varies by model but is typically 128K-200K.

4. Token-efficient by design

Claude Code is optimized for coding workflows — it manages context intelligently, only reading files when needed, and using tools sparingly. Ties naturally to the CLI philosophy.

5. Better model choices for the task

Claude Code lets you pick per session: Opus 4.8 for complex reasoning, Sonnet 5 for balanced work, Haiku 4.5 for fast/cheap. All three are strong at agentic tool use. Copilot has model options too — but the routing and picking varies by tier and organization.

6. Simpler mental model for teaching

This one matters for classroom demos. Students see:

  1. A prompt goes in the terminal
  2. Claude Code runs shell commands
  3. Output appears in the same terminal
  4. Files change on disk — visible in their IDE

Everything happens in one screen. No hidden layers. No "wait, where did it run?" moments.

Fair caveat

Copilot Chat is not "bad" for CLI work. It can run terminal commands via Agent mode. But Claude Code was designed for this shape of workflow from day one. For teaching purposes and clean demos, Claude Code makes life simpler. Use what your team has access to — but if you're picking fresh for CLI work, Claude Code is the natural choice.

06Install Playwright CLI + Skills

Two commands, in this exact order.

Step 1 — Install the CLI package

bash Terminal · install Playwright CLI 
npm install -g @playwright/cli@latest
playwright-cli --version

Step 2 — Create your demo project

bash Terminal · create project 
cd ~/Documents
mkdir pw-cli-demo && cd pw-cli-demo
npm init -y
npm install -D @playwright/test

Step 3 — Install Skills (the step everyone misses)

Now the critical step. Skills do NOT install automatically with the CLI package. You need this separate command, run from inside your project:

bash Terminal · install Skills 
playwright-cli install --skills

Expected output:

output 
✅ Workspace initialized at `/path/to/pw-cli-demo`.
✅ Skills installed to `.claude/skills/playwright-cli`.
✅ Found chrome, will use it as the default browser.
Important note on location

Skills install to <project>/.claude/skills/, NOT to ~/.claude/skills/. This is project-local by design — different projects can use different Skill versions, and you can commit Skills to git for team consistency. Claude Code must be started from this project folder to discover them.

Step 4 — Install browser binaries

bash Terminal · install browsers 
playwright-cli install-browser

Downloads Chromium, Firefox, and WebKit (~450 MB total). One-time step per machine.

Step 5 — Verify everything

bash Terminal · verify installation 
# Verify CLI
playwright-cli --version

# Verify Skills folder exists
ls .claude/skills/playwright-cli/

# Should show: SKILL.md and references/
ls .claude/skills/playwright-cli/references/

# Try one manual command to confirm browsers work
playwright-cli open https://www.google.com --headed
# (Close the browser after it opens)

If all four commands work, you're ready to launch Claude Code.

07Anatomy of the Skill file

Before running any agent, spend two minutes understanding what a Skill actually is. This is the primitive that changes everything.

bash Terminal · peek at SKILL.md 
cat .claude/skills/playwright-cli/SKILL.md | head -40

You'll see something like this:

markdown .claude/skills/playwright-cli/SKILL.md (excerpt) 
---
name: playwright-cli
description: Drive a real browser from the terminal using playwright-cli.
  Handles navigation, snapshots, clicks, typing, screenshots, and test generation.
---

# Playwright CLI Skill

Use `playwright-cli` to drive browsers from the terminal. Commands are
short and token-efficient. Snapshots are saved to disk, not streamed
into context.

## Basic workflow
1. Open a page: `playwright-cli open <url> --headed`
2. Snapshot to get element refs: `playwright-cli snapshot`
3. Interact using refs: `playwright-cli click e21`
4. Re-snapshot after significant DOM changes

## Common commands
- `open <url>` — navigate to URL
- `snapshot` — capture accessibility tree to disk, return element refs
- `click <ref>` — click element by ref
- `type <ref> <text>` — type into a field
- `screenshot [filename]` — save screenshot
- `codegen` — generate Playwright code from actions

## References
See references/ for detailed guides:
- run-tests.md — running and debugging Playwright tests
- test-generation.md — plan / generate / heal workflow
- storage-state.md — cookies and localStorage
- ...

Three important properties

1. It's plain Markdown. Not JSON, not a special format. Any editor can open it. Any agent that reads text can use it.

2. It's small. ~500-1000 tokens total. Compare to MCP's ~3,600 token tool schema load. The upfront cost is 5-7x lower.

3. It's discoverable. Claude Code scans .claude/skills/ automatically. No config, no registration, no server to start. Drop a folder in, restart Claude Code, Skill becomes available.

The design insight

Skills are just documentation the AI reads. That's it. There's no runtime, no protocol, no server. Any tool that can be driven from a terminal can be exposed as a Skill in minutes. This is why the pattern is spreading fast — the barrier to add a new tool is a Markdown file.

The references folder

The main SKILL.md is short — a hub. Deep guides live in references/ and get loaded only when the agent needs them.

bash Terminal · list references 
ls .claude/skills/playwright-cli/references/

Typical output:

output 
run-tests.md
mock-requests.md
run-code.md
session-management.md
storage-state.md
test-generation.md

The test-generation.md reference is what enables Planner-Generator-Healer via CLI. When you ask the agent to "plan tests" or "heal this failing test," it reads this reference and adopts the right behavior.

09Generator via CLI — from plan to test

Now turn scenario 1.1 into a runnable Playwright test.

Set up a minimal framework

Before running the Generator, add two starter files so it has conventions to follow:

bash Terminal · create framework skeleton 
mkdir -p src/pages src/fixtures tests/data
touch src/pages/BasePage.ts src/fixtures/base.ts tests/data/users.json

Fill src/fixtures/base.ts:

typescript src/fixtures/base.ts 
import { test as base, expect } from '@playwright/test';

export const test = base.extend<{}>({});
export { expect };

Fill src/pages/BasePage.ts:

typescript src/pages/BasePage.ts 
import { Page } from '@playwright/test';

export abstract class BasePage {
  protected readonly page: Page;
  constructor(page: Page) { this.page = page; }
  abstract goto(): Promise<void>;
}

Fill tests/data/users.json:

json tests/data/users.json 
{
  "standard": { "username": "standard_user", "password": "secret_sauce" },
  "locked":   { "username": "locked_out_user", "password": "secret_sauce" }
}

The Generator prompt

prompt Claude Code · Generator 
Act as the Generator from the playwright-cli test-generation skill.

Use scenario 1.1 from specs/saucedemo-login.md.

Framework conventions (STRICT):
- Import test and expect from src/fixtures/base.ts,
  NOT from @playwright/test directly
- Page objects live in src/pages/ and extend BasePage
- Load credentials from tests/data/users.json (users.standard)
- Locator priority: getByRole → getByLabel → getByTestId.
  NO CSS, NO XPath, NO waitForTimeout.
- Tag the test title with @smoke @critical

Workflow:
1. Use playwright-cli to verify locators on the live app
2. Ask before creating any new page object file
3. Create LoginPage.ts and InventoryPage.ts as needed
4. Save the spec at tests/auth/standard-login.spec.ts
5. Run the test with: npx playwright test tests/auth/standard-login.spec.ts
6. Fix and re-run until it passes
7. Report the final files and pass output

What you'll see

The agent will:

  1. Open the SauceDemo login page via CLI
  2. Snapshot to identify locators
  3. Ask you to confirm creating LoginPage.ts — approve
  4. Ask about InventoryPage.ts — approve
  5. Write the test file
  6. Run the test
  7. Iterate if anything fails

Sample generated test

The output should look like this:

typescript tests/auth/standard-login.spec.ts 
import { test, expect } from '../../src/fixtures/base';
import { LoginPage } from '../../src/pages/LoginPage';
import users from '../data/users.json';

test.describe('SauceDemo login', () => {
  test('standard user logs in and lands on inventory @smoke @critical',
    async ({ page }) => {
      const login = new LoginPage(page);
      await login.goto();
      const inventory = await login.loginAs(users.standard);

      await expect(page).toHaveURL(/inventory\.html/);
      await expect(inventory.header).toHaveText('Products');
      await expect(inventory.productCards).toHaveCount(6);
    });
});

Verify by hand:

  • Imports come from ../../src/fixtures/base, not @playwright/test
  • page.getByRole is not called directly in the test — locators live in page objects
  • No CSS selectors, no XPath, no waitForTimeout
  • Tag applied to test title
Review discipline

If any of these are violated, do NOT accept the code as-is. The AI generated it. Your job is to review it against your framework rules. This review skill is where engineering judgment lives — and where fundamentals pay off.

10Healer via CLI — diagnose and fix

The Healer is the third role. It diagnoses a failing test, identifies root cause, and produces a minimum-viable fix — without weakening the assertions.

Step 1 — Break the test intentionally

Open src/pages/LoginPage.ts. Find the username locator and change the accessible name:

typescript src/pages/LoginPage.ts (introduce a break) 
// Original — works
readonly usernameInput = this.page.getByRole('textbox', { name: 'Username' });

// Broken — typo in the accessible name
readonly usernameInput = this.page.getByRole('textbox', { name: 'User Name' });

Save. Confirm the test now fails:

bash Terminal · reproduce the failure 
npx playwright test tests/auth/standard-login.spec.ts

You should see a timeout error waiting for the locator.

Step 2 — The Healer prompt

prompt Claude Code · Healer 
Act as the Healer from the playwright-cli test-generation skill.

The test tests/auth/standard-login.spec.ts is failing.

Diagnose and fix using the healing discipline:

1. Run the test to reproduce the failure
2. Read the error output carefully
3. Use playwright-cli to open the app and inspect the actual DOM
4. Classify the failure (locator drift / UI restructure / real regression)
5. Apply the minimum-viable fix
6. PRESERVE assertion intent — do NOT weaken any assertion
7. Do NOT add waitForTimeout, do NOT skip the test,
   do NOT increase timeouts
8. Re-run the test twice to confirm stability
9. Produce a Healer Report explaining what you did and why

If root cause looks like a real bug in the app, STOP and report —
do not modify the test to hide it.

What a good Healer output looks like

markdown Healer Report (excerpt) 
## Healer Report — tests/auth/standard-login.spec.ts

### Failure classification
A — Locator drift

### Root cause
The LoginPage.usernameInput locator uses accessible name "User Name"
(with space). The actual DOM element has accessible name "Username"
(no space). Verified via playwright-cli snapshot on the live app.

### Fix applied
Changed the accessible name back to "Username" in
src/pages/LoginPage.ts, line 8.

### Intent preservation check
- Original assertion: expect(page).toHaveURL(/inventory\.html/)
- New assertion: (unchanged)
- Did assertion intent change? NO
- Was any assertion softened? NO
- Was any test skipped? NO
- Was any timeout increased? NO

### Test result
- Run 1: PASS
- Run 2: PASS

### Recommendation
Ready to merge — clean fix.

The critical review question

Every Healer PR must be reviewed with one question: did the Healer fix the test, or fix the pass/fail status?

Watch for these red flags in Healer output:

  • Assertion changed from toHaveCount(6) to toBeVisible()
  • Assertion changed from toHaveText to toContainText
  • New waitForTimeout(5000) added
  • Test marked test.fixme or test.skip
  • Timeout increased beyond your config default
  • Page object modified when only the spec was supposed to change

Any of these — reject the fix. Fix by hand instead.

You've now used both approaches. Here's how they actually differ, feature by feature.

The single biggest structural difference

MCP streams page state INTO the model's context. CLI keeps it ON disk and reads only when needed.

This is the entire architectural difference in one sentence. Every other difference — token cost, context growth, wall-clock time, cost at scale — flows from this one design choice.

12Token consumption breakdown

Where do tokens actually get spent in an AI-driven browser session? Five places. Let's break them down individually, then compare.

1. Tool schema loading (upfront, once per session)

MCP
3,600
Full JSON schemas for all browser tools
CLI + Skills
~68
Just the SKILL.md description

2. Page snapshots (recurring, biggest cost)

This is the killer. Every browser interaction that changes the page needs a fresh snapshot.

MCP · per snapshot
15-25K
Full accessibility tree streamed into context
CLI · per snapshot
~15
Just "Saved to snapshot.yaml"

And critically — with CLI, the agent reads the yaml file only when it needs specific information. Most snapshots never actually enter the context window.

3. Tool call return values

MCP · per return
8-20K
Structured response with page state
CLI · per return
~10
Terminal confirmation: "✓ Clicked element e21"

4. Context accumulation (the compounding cost)

MCP's snapshots stay in conversation history. Every subsequent reasoning step re-reads them. After 10 snapshots, your context is bloated with page states you're no longer looking at.

CLI's snapshots live on disk. Conversation history only has file paths. Context stays lean throughout the session.

The "lost in the middle" effect

Studies of transformer models show attention quality degrades past ~60% context fill. Snapshots piled up in MCP sessions push you past this threshold fast. Result: your LLM reasons worse on turn 15 than it did on turn 3. CLI avoids this entirely.

5. Reasoning tokens (same both ways)

LLMs need tokens to think. The LLM's own reasoning is roughly the same in both cases — same problem, same intelligence needed to solve it. Difference: CLI mode gets higher quality reasoning because context is cleaner.

Same task — full comparison

Microsoft's benchmark, same task both ways: "Explore a 20-page e-commerce app, add items to cart, complete checkout."

  • Run 30 nights per month

MCP: 100 × 20 × 20,000 = 40M tokens per night × 30 = 1.2B tokens/month → ~$3,600/month at Sonnet pricing

CLI: 100 × 20 × 500 = 1M tokens per night × 30 = 30M tokens/month → ~$90/month at Sonnet pricing

Monthly savings: $3,510. Annual: $42,000. This pays for two junior QA engineers.

13When to use which

Not one-size-fits-all. Both have their place.

Use CLI + Skills when...

  • Running agents in CI/CD pipelines — cost matters, token efficiency matters
  • Long automation sessions (20+ steps) — CLI's clean context stays coherent
  • Batch test generation — 100 tests × many steps × many days
  • Working with coding agents that combine browser + code — Claude Code, Codex, Cursor Agent
  • Your project uses large repos — you want the LLM's context free for reading your code, not choked with page snapshots
  • You need reproducible, audit-able, scriptable automation — shell commands you can log, replay, debug
  • Cost-sensitive projects — startups, tight budgets, high-frequency runs

Use MCP when...

  • Sandboxed environments — Claude Desktop, web-based agents that can't run shell commands
  • Interactive exploration — you want the LLM to see everything about the page in real-time
  • Locator hunting — quick "help me find a good locator for this element" sessions
  • Self-healing workflows with rich introspection — where the agent benefits from persistent, deeply-loaded page state
  • Short sessions — 3-5 turns, where token cost is negligible
  • You're on Copilot Free/Pro and want a built-in solution — MCP integrates directly with the Copilot Chat modes

Use both when...

Many teams do this. Different tool for different job:

  • CLI — for CI/CD, test generation, long autonomous runs
  • MCP — for interactive debugging in IDE, exploratory locator work

Think of it like git and gh — both are Git-related tools, both have their place. Same here.

MCP is a rich API. CLI is a set of shell commands. Pick MCP for rich introspection; pick CLI for lean throughput.

14Common pitfalls

Forgetting to install Skills

The #1 mistake. Installing @playwright/cli does NOT install Skills. Run playwright-cli install --skills separately, from inside your project.

Starting Claude Code from the wrong folder

Skills are project-local at .claude/skills/. Claude Code must be started from the project root — otherwise it doesn't see them. Symptom: agent says "I don't see any Playwright Skill."

Assuming CLI = faster (wall-clock)

CLI is more token-efficient, not always faster in wall-clock time. It sometimes takes extra round trips reading yaml files. The savings are in cost and reasoning quality, not raw speed.

Not restarting Claude Code after Skill install

Skills are discovered at startup. If you installed Skills while Claude Code was running, exit (/exit) and restart.

Using Opus for simple tasks

Opus is powerful but expensive. For basic test generation, Sonnet or Haiku is more cost-effective and often faster in practice. Save Opus for complex refactors and deep debugging.

Trusting Healer output blindly

Same warning as with MCP. Never merge a Healer fix without reading the diff. The most common failure mode is silent test weakening — Healer changes an assertion to make the test pass, but now it doesn't catch the original bug.

Skipping the SKILL.md read

Sometimes the agent doesn't automatically read the SKILL.md at session start. Add "read .claude/skills/playwright-cli/SKILL.md" explicitly to your first prompt if you notice the agent guessing at commands.

Prompting without saying "use playwright-cli"

Explicitly mention playwright-cli in your prompt. Otherwise the agent may try to use @playwright/test code directly (which is fine, but skips the CLI benefits).

Committing browser cache to git

Add these to .gitignore:

bash .gitignore 
node_modules/
.playwright/
test-results/
playwright-report/

# Keep Skills tracked — they're team documentation
# .claude/skills/  ← DO NOT ignore this

Commit your Skills to git — they're team documentation. Ignore the .playwright/ browser cache and snapshot temp files.

15Final thoughts

Three months ago, "AI agents for testing" meant MCP. Today it means MCP or CLI + Skills. Six months from now there'll likely be a third or fourth option. The tools change. The fundamentals don't.

Learn to evaluate tools, not just use them. That is the meta-skill worth building.

Three habits worth building

  1. Read the SKILL.md. Not just for Playwright — for every tool you use. Skills are documentation. Understanding them makes you a better prompter.
  2. Read every diff. AI generates code. Your job is to review it. This is where fundamentals pay off — you can't review what you don't understand.
  3. Measure your tokens. Run /status in Claude Code periodically. Track cost per task. Optimize when it matters. Ignore when it doesn't.

The bigger shift

The role of a test engineer isn't becoming "prompt writer." It's becoming reviewer, guardrail, architect. Those roles come from fundamentals — framework knowledge, locator strategy, assertion discipline, understanding why weakened tests kill coverage.

AI turns those roles from valuable into critical. An engineer who understands the framework becomes 3-5x more productive with AI. An engineer who doesn't ships plausible-looking test debt at scale.

Use CLI where it makes sense. Use MCP where it makes sense. Use both if both fit your workflow. But always — always — review harder than you write.
